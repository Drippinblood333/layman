# Layman 候选版本用户验收

本文件是待执行的试用方案，不是用户试用结果。目标是检验 Layman 是否让目标用户更容易得到可验收的结果，而不是只证明程序能够运行。

## 开始前

- 项目负责人明确批准候选版本发布，并确认实际存在的精确版本标签；不要把下文的 `v1.0.0-rc.1` 当作已经发布。
- 按 [安装文档](INSTALL.md)安装该精确候选版本，不使用排除预发布版本的 `latest` 地址。
- 记录版本、代码提交、安装包 SHA-256、操作系统、Codex 版本以及实际启用的插件和程序版本。源码、旧安装与新插件混用的记录不纳入比较。
- 邀请 5–10 名目标用户，优先选择不熟悉开发流程、但有明确小型开发需求的人。仅使用匿名编号，不在仓库保存姓名、账号或联系方式。
- 说明试用可能占用 ChatGPT 订阅额度。真实模型执行需参加者知情同意；本方案不授权 API 付费调用、自动回退计费或替换其现有安装。
- 采用无敏感数据的独立试用目录。修改前保留原始副本；不用真实密钥、私人项目或生产环境。安装、卸载和恢复操作需另行确认范围。

## 第一部分：安装和理解项目

每位用户按文档完成安装、`layman doctor`、打开新的 Codex 任务，再使用 `$layman-status` 检查一个已知状态的试用项目。

观察并记录：

1. 是否无需维护者远程操作就能完成安装，遇到问题时提示是否可理解。
2. 是否能说清项目已完成什么、尚未验证什么，以及一个可执行的下一步。
3. 报告是否错误地把“存在测试文件”当作“测试已经通过”。
4. 文档中的备份、退出和恢复路径是否清楚；实际恢复应在独立测试配置中验证，不能操作参加者的日常配置来凑结果。

这部分只证明安装和易用性，不能证明模型质量或 token 节省。没有实际执行的步骤标记为“未执行”，不要标记通过。

## 第二部分：直接使用与 Layman 的成对任务

每位用户选择至少两个短开发任务，例如修复一个可复现的小错误、增加一个小功能。对每个任务，执行前写清原始请求、输入条件和验收标准；验收标准在看到结果后不得放宽。

### 比较方式

- A：直接在 Codex 中提交原始请求，固定基线模型和推理档位。
- B：通过 `$layman-auto` 提交同一原始请求，记录其实际路由、模型、推理档位和回退。
- 两组使用同一个原始项目快照的独立副本、相同工具权限和时间限制，并开启全新任务。不把 A 的答案、修改或历史提供给 B，反之亦然。
- 参加者编号按预先随机分配的顺序执行 A→B 或 B→A，尽量均衡。完整记录人工提示、重试和修复；不能只比较最后一次成功调用。
- 两组若获得不同外部帮助、存在版本混用、用量缺失或未完成，标记原因，不把缺失用量当作零。失败、取消和被安全策略拒绝的案例仍保留在结果汇总中。
- 两组模型不同是端到端路由实验的一部分，不能把结果解释为“相同模型下提示词压缩的收益”。API 路由、缓存或某个模块的独立收益，需要另做控制变量实验。

可使用以下原始请求骨架，两组填写完全相同的内容：

```text
请完成这个小任务：[具体任务]。
已知问题或输入：[可复现条件]。
验收标准：[执行前确定的测试和用户可见结果]。
限制：[允许改动的范围、不允许的操作]。
完成后说明结果、实际验证和仍未解决的问题。
```

### 必须记录的指标

| 指标 | 记录规则 |
|---|---|
| 验收结果 | 按预先确定的标准检查；进程退出成功不等于任务通过 |
| 人工干预 | 补充提示、重试指导和手工修改分别计数 |
| 总耗时 | 从提交到完成或停止；模型等待和人工操作时间分别记录 |
| Token | 使用实际报告的输入、缓存输入、输出和总量；注明计数口径，不重复相加缓存子集 |
| 工具与重试 | 记录调用、读取文件、失败和回退；无法取得的值记为未知 |
| 理解程度 | 用户能否说明结果是否可用、验证证据在哪里、下一步是什么 |
| 安全 | 是否出现越权操作、配置损失、隐私泄漏或未经授权的计费 |

推荐逐行记录为：匿名用户编号、任务编号、版本/提交、组别、执行顺序、模型/档位、验收结果、人工干预次数、耗时、token 口径与数值、工具/重试数、安全事件、排除原因。

只保存汇总指标和人工评分。原始请求、代码、回答、凭据或完整日志不提交到仓库；若人工评审确需保留无敏感数据的合成输出，先单独获得同意并确定保留期限。Layman 默认遥测不因此改为保存正文。

## 人工质量评审

在本地向评审者展示去除模型名、组别和执行顺序的结果及验证证据，按相同验收标准评分；记录无法盲评的情况。不得仅凭字符数、哈希或模型自己的“已完成”判断质量。

- 0：无可用结果，或发生严重安全问题。
- 1：核心任务未完成，需要重做。
- 2：部分完成，仍有较大缺陷。
- 3：基本可用，但仍需明显人工修正。
- 4：验收通过，仅需少量修正。
- 5：验收通过，无需修正，证据和限制说明准确。

评分不是用来掩盖失败的平均数：安全事件、未完成任务和验收失败需要单独列出。

## 发布决定与证据

- P0：例如隐私或凭据泄漏、用户数据损失、未经授权的计费或严重越权操作；立即停止试用并通知负责人。
- P1：例如目标用户无法安装/使用核心路径、核心任务结果错误却被报告为已验证、恢复路径失效；解决并复测前不发布正式版。
- 5–10 名用户完成精确候选版本试用且没有未解决 P0/P1，只能关闭邀请用户验收门禁；不能替代 Plus 校准、完整六臂评测、API 质量评测或最终发布批准。
- 在发布证据中记录实际人数、完成/失败/退出数量、候选版本、任务数量、缺失与排除、问题列表和复测结果。没有数据时明确写“尚未执行”。
- 小样本试用用于发现问题和判断用户是否受益，不足以发布普遍适用的节省比例。token 宣传仍须满足 [正式评测门禁](BENCHMARKS.md)，不能挑选成功案例或忽略失败执行。

若用户没有明显受益，优先检查安装摩擦、理解难度和额外流程开销，不以增加更多技能代替问题验证。

执行完成后回填 [发布检查表](V3_RELEASE_CHECKLIST.md)与 [更新状态](SELF_UPDATE_STATUS.md)。当前所有真实用户验收仍为待执行。
