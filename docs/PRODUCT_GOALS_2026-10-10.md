# Layman 产品目标与自更新约束

用户原始目标：

1. 项目安装简单，体积小。
2. 上手简单，可以针对写得不好的 prompt 进行优化。
3. 避免过度设计、过度测试，精简输入输出。
4. 节省 token。

## 可验收的结果

| 目标 | 实现与验收要求 |
| --- | --- |
| 安装简单、体积小 | 默认安装不要求手动配置 Python 或 API key；记录各平台下载大小、安装后大小、依赖数量与首次可用步骤。与当前版本比较后确定精简目标，不编造已实现的缩减幅度。可选代理、模型、适配器不挤进默认安装。保留校验、升级回退与安全卸载。 |
| 上手与 prompt 优化 | 用户直接描述需求即可；仅对缺失的关键目标、约束和验收条件补充结构。原始需求不变，不凭空添加需求或扩大权限；影响结果的歧义才提问。简单任务不强制增加一次模型调用。用预先选定的模糊需求、明确需求、否定约束和高风险需求验证。 |
| 精简工作与输入输出 | 优先复用现有代码、标准库和平台功能；Ponytail 等规则按需融合而非重复堆叠。按变更风险选择验证范围，不因仓库处于发布候选阶段就为每个小任务跑全套发布检查。首次相关测试、失败定位和影响面检查不能省；大范围/安全/安装/发布变更需要相称验证。保留错误、退出状态、关键事实、代码语义与风险说明。 |
| 节省 token | 对相同任务、相同验收标准测总输入/输出、缓存/非缓存、重试、耗时和成功率，计算一次成功交付的总消耗。把优化器自身的提示、模型调用和恢复原文计入。日志字节压缩、短回答和换便宜模型不等于全任务 token 节省。只有质量不下降且有代表性实测改善，才能宣称有效；负结果必须保留。 |

## 推进顺序

1. 修复规划器误读否定约束与无关全套发布检查建议；测默认安装和常驻提示的基线。
2. 提供轻量默认路径和忠于原意的 prompt 整理；避免为整理本身新增必需模型调用。
3. 融合 Ponytail 的最小完整修改规则，评估 RTK 可选适配器；明确订阅与 API 路径各自真正支持的能力。
4. 在新批准的评测预算内比较真实开发任务；未证明收益的优化保持可关闭或移除。Headroom、LLMLingua 等重依赖不默认引入。

复制或捆绑上游内容前核对具体版本、许可证、NOTICE 与依赖；保留来源与修改记录。不把多个项目的宣传百分比相加。

## 长期任务如何停止浪费

- 每批只解决一个有证据的产品问题，留下短记录：改了什么、验证了什么、下一项是什么。
- 不重复扫描未变更文件，不重复运行已通过且无相关变化的检查，不以更新文档制造进展。
- 连续优化没有实测收益时停止该策略并保留结论；没有可行动问题时不制造重构或测试。
- 长期维护不等于无限活动目标：以可验收的版本里程碑为目标；完成一批后报告事实，后续维护沿用已有定时机制，不新建重复自动化。
- 自动继续不扩张授权。现有 12、36、8 次评测批准均已耗尽；新增模型评测、付费 API、发布标签/正式发布、替换现有安装仍需相应明确批准。人工质量评分与真实用户试用不能伪造。
- 对目标模式的措辞和应用状态分开报告：本文件定义产品目标，不表示应用中的旧目标已被替换或重新启动。
