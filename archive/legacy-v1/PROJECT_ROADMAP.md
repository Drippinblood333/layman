# Layman Skill 项目路线与商业可行性分析

版本：v0.1  
日期：2026-06-18  
定位草案：面向 AI Coding 新手的项目落地导航器

## 1. 一句话结论

本项目具备较高可行性和中高商业价值，但不应定位为普通的 Prompt 生成器。

更准确的定位是：

> 帮助非专业开发者和 AI Coding 新手，把模糊创意转化为可执行、可验证、低 token 浪费、可维护、可发布的软件项目路线。

项目第一阶段应以 Codex / Claude Code / Cursor 等 AI coding agent 的任务规划 Skill 形态落地，核心目标不是直接“一键生成完整项目”，而是让用户每一步都知道应该让 AI 做什么、怎么验收、什么时候停止。

## 2. 项目背景

AI coding 工具正在快速普及，Codex、Claude Code、Cursor、Gemini CLI 等工具已经让普通人具备了更低成本开发软件的可能。但现实问题是，很多新手并不是卡在模型能力上，而是卡在如何正确指挥模型。

典型错误包括：

- “帮我优化整个项目。”
- “运行一个小时，尽可能完善我的项目。”
- “你自己看着改。”
- “帮我做一个完整 App。”
- “把所有问题都修好。”

这些 prompt 的问题不只是表达不清，而是缺少工程任务的基本要素：

- 明确目标
- 范围边界
- 优先级
- 可验证结果
- 停止条件
- 风险限制
- 文件修改权限
- 测试和发布标准
- 维护策略

结果是 agent 容易全仓库乱扫、反复读取上下文、生成大范围 diff、陷入多轮修错，造成 token 浪费和项目质量失控。

## 3. 从 Caveman 现象得到的启发

JuliusBrussee/caveman 的爆火说明一个明确趋势：AI agent 用户已经开始强烈关注 token 浪费、输出冗余和 agent 行为可控性。

Caveman 的主要价值是让模型少说废话，压缩输出 token。它的传播成功来自：

- 承诺足够清晰：少说废话，省 token。
- 记忆点强：原始人说话风格。
- 安装简单：skill / plugin 形态清晰。
- 数据可传播：宣称最高节省 87% token。
- 多工具适配：Claude Code、Codex、Cursor、Gemini 等。

但评论区争议也暴露了更深层问题：coding agent 真正的大量消耗往往不是最终回答，而是输入侧和上下文侧：

- 反复读源码
- 多轮对话历史累积
- 工具调用结果进入上下文
- 日志和错误输出膨胀
- 每轮请求都带上大量历史和文件内容
- 任务没有边界导致 agent 不断探索

因此，本项目不应照抄 Caveman 的“压缩输出”路线，而应主攻更靠前的问题：

> 防止用户从第一句话开始就把 agent 带入高 token、低质量、不可验收的执行路径。

## 4. 核心愿景

长期愿景：

> 让每个有创意的人，都能借助 AI coding 工具，把想法落地成可维护、可发布的软件项目。

这不是“让不会写代码的人一次性生成完整项目”，而是让用户完成一条可靠路径：

```text
创意
-> 需求澄清
-> MVP 定义
-> 技术路线
-> 任务拆解
-> Agent prompt
-> 分阶段实现
-> 测试验收
-> 文档整理
-> 部署发布
-> 后续维护
```

## 5. 产品本质

本项目的本质不是 Prompt Generator，而是三种能力的组合：

1. 创意澄清器  
   把模糊想法转成产品需求、用户场景和 MVP 范围。

2. 项目导航器  
   把需求转成分阶段路线图，并告诉用户每一步应该做什么。

3. Agent 任务编译器  
   把每一步转成适合 Codex / Claude Code / Cursor 执行的低风险 prompt。

## 6. 目标用户

### 6.1 第一优先级用户

- 刚开始使用 Codex / Claude Code / Cursor 的新手
- 有创意但缺少工程经验的人
- 想用 AI 做独立项目的学生
- 产品经理、设计师、运营、自媒体创作者
- 想做副业工具、小程序、网站、自动化脚本的人
- 会一点代码但不懂项目工程化的人

### 6.2 第二优先级用户

- 独立开发者
- 小团队技术负责人
- AI coding 教程作者
- 编程教育机构
- 创业早期团队

### 6.3 暂不优先服务的用户

- 大型企业研发团队
- 强合规行业
- 已有成熟工程平台的专业团队
- 只想要“一键生成完整项目”且不愿理解过程的用户

原因：这些用户需求复杂，第一阶段服务成本高，不适合 MVP 验证。

## 7. 用户核心痛点

### 7.1 不知道如何开始

用户有一个想法，但不知道第一步应该让 AI 做什么。

错误做法：

```text
帮我做一个背单词 App。
```

更好的第一步：

```text
请先把我的想法拆成 MVP，不要写代码。输出目标用户、核心场景、首版功能、暂不做功能、数据结构草案和第一阶段开发任务。
```

### 7.2 不知道任务多大才合适

新手倾向于让 agent 一次性完成太多事情。大任务会导致上下文膨胀、错误增多、难以 review。

项目应帮助用户把任务控制在 15-45 分钟内可完成、可验证的粒度。

### 7.3 不知道怎么验收

很多新手只看“AI 说完成了”，但不知道项目是否真的能运行、功能是否可用、部署是否完整。

项目应强制生成验收标准，例如：

- 页面能打开
- 命令能运行
- 测试通过
- 构建通过
- README 包含启动方式
- 环境变量有示例
- 不修改无关文件
- 不新增不必要依赖

### 7.4 害怕 AI 乱改

AI coding agent 强在执行，但如果任务没有边界，容易修改过多文件。

项目应自动加入安全边界：

- 先分析，不改代码
- 修改前先给计划
- 超过指定文件数先询问
- 不新增生产依赖
- 不重构公共 API
- 不格式化全仓库
- 不删除用户文件
- 失败时停止并报告原因

### 7.5 不知道如何从原型走到发布

很多 AI 生成项目停留在 demo 阶段，缺少：

- 错误处理
- 数据持久化
- 配置说明
- 测试
- 部署脚本
- 用户文档
- 维护计划

项目应把“可发布”作为路线图的一部分，而不是只生成代码。

## 8. 产品定位

推荐中文定位：

> AI Coding 项目导航器：把你的创意拆成可执行、可验收、可发布的 AI 编程任务。

推荐英文定位：

> A project navigator that turns vague ideas into safe, verifiable coding-agent tasks.

不建议使用的定位：

- Prompt 生成器
- AI 写代码助手
- 一键生成 App 工具
- 省 token 神器

原因：这些定位要么太泛，要么容易被官方工具替代，要么会引导用户期待失真。

## 9. 产品差异化

### 9.1 与普通 Prompt 模板库的区别

普通模板库提供固定文案。本项目提供任务判断、范围控制、验收标准和下一步路线。

### 9.2 与 Caveman 的区别

Caveman 主要压缩输出。本项目主要减少输入侧浪费和任务失控。

### 9.3 与 Codex / Claude Code 内置能力的区别

官方工具会越来越强，但它们通常关注执行能力。本项目关注用户从想法到任务的前置规划，以及新手可理解的项目落地流程。

### 9.4 与一键建站 / 低代码平台的区别

一键平台往往生成封闭结果。本项目是帮助用户使用通用 AI coding agent，并保留项目的可维护性和可迁移性。

## 10. 产品形态路线

### 阶段 1：Skill MVP

目标：验证用户是否需要“从创意到 agent 任务”的规划能力。

形态：

- Codex Skill
- Claude Code Skill
- Markdown 模板和参考资料

核心能力：

- 创意澄清
- MVP 拆解
- Prompt 体检
- 安全任务生成
- 验收标准生成
- token 风险提示

优点：

- 开发成本低
- 可快速迭代
- 容易开源传播
- 适合借 AI coding 社区传播

### 阶段 2：CLI / 本地工具

目标：增加项目感知能力。

能力：

- 扫描项目结构
- 识别技术栈
- 识别 package manager
- 识别测试、lint、build 命令
- 读取 README、AGENTS.md、CLAUDE.md
- 检查 git diff
- 生成下一步任务建议

示例：

```text
layman analyze
layman plan "我想加登录功能"
layman prompt --target codex
layman check-prompt "帮我优化整个项目"
```

### 阶段 3：插件形态

目标：嵌入 AI coding 工具的真实使用流程。

可做能力：

- prompt 提交前检查
- 高风险 prompt 拦截
- 一键改写为安全任务
- 状态栏显示 token 风险
- 项目规则自动生成
- 任务模板选择

适配方向：

- Codex 插件或 Skill 体系
- Claude Code plugin / hooks
- Cursor rules / prompt templates
- VS Code 扩展

### 阶段 4：Web 产品

目标：面向小白提供可视化项目导航。

能力：

- 创意输入
- 问答式需求澄清
- MVP 看板
- 技术路线图
- AI agent prompt 队列
- 项目阶段追踪
- 发布检查清单
- 维护任务推荐

### 阶段 5：团队版

目标：面向小团队和教育机构。

能力：

- 团队 prompt 规范
- 项目模板库
- AGENTS.md / CLAUDE.md 规则生成
- 代码变更风险清单
- 项目健康报告
- 新手 onboarding 流程
- 课程和训练任务集

## 11. MVP 功能设计

第一版只做 5 个核心场景。

### 11.1 创意转项目计划

输入：

```text
我想做一个给学生背单词的小程序。
```

输出：

- 目标用户
- 核心场景
- MVP 功能
- 暂不做功能
- 数据结构草案
- 页面/接口草案
- 推荐技术栈
- 分阶段开发计划
- 第一条可交给 Codex 的 prompt

### 11.2 模糊 prompt 体检

输入：

```text
帮我完善整个项目。
```

输出：

- 风险等级
- 主要问题
- token 浪费原因
- 安全改写版本
- 推荐先执行的只读分析任务

### 11.3 安全任务生成

输入：

```text
我想给现有项目加登录功能。
```

输出：

- 先分析 prompt
- 实现 prompt
- 测试 prompt
- 文档 prompt
- 每一步停止条件

### 11.4 新手项目接手

输入：

```text
我刚下载了一个项目，不知道怎么开始。
```

输出：

- 只读项目理解 prompt
- 技术栈识别 prompt
- 启动项目 prompt
- 第一个小修复任务建议

### 11.5 发布前检查

输入：

```text
项目差不多做完了，怎么发布？
```

输出：

- 构建检查
- 环境变量检查
- README 检查
- 错误处理检查
- 安全检查
- 部署平台建议
- 发布 prompt

## 12. Skill MVP 建议结构

建议仓库结构：

```text
layman_skill/
  skills/
    layman-project-navigator/
      SKILL.md
      references/
        prompt-scorecard.md
        task-patterns.md
        project-stages.md
        bad-prompts.md
        release-checklist.md
      agents/
        openai.yaml
  examples/
    bad-to-good-prompts.md
    idea-to-roadmap.md
    project-handoff.md
  evals/
    prompts.json
    expected-output-rubric.md
  PROJECT_ROADMAP.md
```

### 12.1 SKILL.md 应保持精简

SKILL.md 只放核心流程，不放大量模板。

原因：Skill 本身会占用上下文，必须遵守渐进式加载原则。

### 12.2 references 放详细模板

不同场景的模板拆到 references：

- `prompt-scorecard.md`：prompt 评分标准
- `task-patterns.md`：bugfix、feature、refactor、review、test 模板
- `project-stages.md`：从想法到发布的阶段定义
- `bad-prompts.md`：坏 prompt 案例库
- `release-checklist.md`：发布验收标准

### 12.3 evals 用于形成护城河

要尽早建立测试集，而不是只写模板。

评测样例：

```text
坏 prompt: 帮我优化整个项目
预期输出:
- 必须指出范围过大
- 必须建议先只读分析
- 必须限制修改权限
- 必须生成验收标准
- 不允许直接建议全仓库重构
```

## 13. 核心输出格式

每次生成任务时，建议固定输出以下结构：

```text
原始需求：

风险判断：

主要问题：

建议拆分：

推荐先执行的任务：

可复制给 Codex 的 prompt：

验收标准：

停止条件：

不建议现在做的事：

下一步：
```

固定格式的好处：

- 新手容易理解
- 可比较
- 可评测
- 可扩展到插件 UI
- 可沉淀数据集

## 14. Prompt 风险评分体系

建议评分维度：

| 维度 | 低风险 | 高风险 |
|---|---|---|
| 目标清晰度 | 有明确结果 | 只有“优化”“完善” |
| 范围控制 | 限定模块/文件 | 全项目无限制 |
| 修改权限 | 明确允许/禁止 | 让 agent 自己决定 |
| 验收标准 | 有测试/构建/人工验收 | 没有完成定义 |
| 停止条件 | 知道何时停 | 无限尝试 |
| token 风险 | 只读必要上下文 | 全仓库扫描 |
| 输出格式 | 要求计划和总结 | 无要求 |

风险等级：

- 低：可直接交给 agent 执行
- 中：建议补充范围和验收标准
- 高：不建议执行，应先改写
- 极高：可能导致大范围破坏或 token 失控，必须拆分

## 15. Token 节省逻辑

本项目节省 token 的方式不是让 AI 少说话，而是减少无效输入和无边界探索。

主要机制：

1. 减少错误启动  
   防止用户一开始就给出大而空的任务。

2. 减少无关文件读取  
   限定 agent 先读哪些文件，不让其全仓库乱扫。

3. 减少多轮返工  
   通过验收标准和停止条件降低试错轮数。

4. 减少大 diff  
   限制修改范围，避免生成难以 review 的改动。

5. 减少上下文膨胀  
   每一步任务独立、短小、可结束，避免长对话持续累积。

6. 减少用户追问  
   输出下一步建议，让用户少用模糊追问补救。

## 16. 商业价值分析

### 16.1 商业价值判断

商业价值：中高。

原因：

- AI coding 工具普及速度快。
- 新手使用门槛真实存在。
- token 成本和上下文浪费正在成为显性痛点。
- 从 demo 到可发布项目的断层明显。
- 市场上缺少专门面向小白的 agent 项目导航工具。

### 16.2 用户愿意付费的原因

用户不是为 prompt 文案付费，而是为以下结果付费：

- 少走弯路
- 少烧 token
- 项目能跑起来
- AI 不乱改
- 知道下一步做什么
- 能从 demo 走到发布
- 项目后续能维护

### 16.3 可收费功能

免费版：

- 基础 prompt 体检
- 创意转 MVP
- 生成 3-5 个任务
- 基础 Codex prompt

Pro 版：

- 完整项目路线图
- 多工具 prompt 输出
- 仓库结构分析
- token 风险分析
- 发布检查
- 维护计划
- 更多项目模板

团队版：

- 团队规则库
- 项目模板库
- 新成员 onboarding
- 统一 AGENTS.md / CLAUDE.md
- 项目健康报告
- prompt 质量统计
- 课程和训练集

### 16.4 可能的商业模式

1. 开源 Skill 引流  
   用免费 skill 建立影响力和案例库。

2. 付费模板包  
   针对独立开发、学生毕设、SaaS、小程序、自动化脚本等提供专业路线。

3. Pro CLI / 插件  
   提供本地项目分析、prompt 风险拦截、发布检查。

4. Web 订阅  
   提供可视化项目路线、任务队列、历史记录。

5. 教育合作  
   给 AI 编程课程、训练营、学校项目提供标准化流程。

6. 团队版  
   面向小团队提供统一 AI coding 使用规范。

## 17. 竞争分析

### 17.1 潜在竞争者

- Codex / Claude Code / Cursor 官方内置功能
- prompt 模板库
- AI 编程课程
- 低代码平台
- 一键生成 App 工具
- GitHub 上的 agent workflow 项目

### 17.2 本项目优势

- 更贴近新手真实问题
- 同时覆盖创意、任务、验收、发布
- 不绑定单一 coding 工具
- 可从 skill 低成本启动
- 可用真实坏 prompt 数据形成评测集
- 可借 token 节省话题传播

### 17.3 本项目劣势

- 初期容易被认为只是 prompt 模板
- 用户可能不愿多走一步
- 官方可能快速补齐部分能力
- 很难直接量化“项目成功率”
- 新手需求分散，场景很多

## 18. 护城河设计

长期护城河不在 prompt 文案，而在以下资产：

1. 坏 prompt 案例库  
   收集真实用户如何错误使用 AI coding agent。

2. 改写数据集  
   每个坏 prompt 对应安全、可执行、低 token 的版本。

3. 任务拆解方法论  
   针对不同项目类型形成稳定路线。

4. 项目阶段模型  
   定义从想法到发布的每一阶段检查项。

5. 评测体系  
   判断一个输出是否真的降低风险和 token 浪费。

6. 工具适配层  
   针对 Codex、Claude Code、Cursor、Gemini CLI 输出不同格式。

7. 新手体验  
   让不懂工程的人也能知道下一步。

## 19. 主要风险与应对

### 19.1 风险：范围过大

问题：从创意到发布是一个很大的目标，容易一开始做成巨型平台。

应对：

- 第一版只做 Skill。
- 第一版只做 5 个场景。
- 第一版不做自动写代码，只生成路线和 prompt。

### 19.2 风险：被认为是普通 prompt 工具

问题：prompt 工具太多，用户可能觉得没有差异。

应对：

- 强调“项目落地导航”。
- 输出路线图、验收标准、停止条件。
- 展示坏 prompt 到好任务的真实案例。

### 19.3 风险：官方工具内置类似能力

问题：Codex、Claude Code、Cursor 可能内置 prompt 改写。

应对：

- 做跨工具。
- 做项目阶段管理。
- 做教育和团队规范。
- 积累案例和评测数据。

### 19.4 风险：用户不愿多走一步

问题：用户可能想直接让 AI 干活，不想先规划。

应对：

- 输出必须短、直接、可复制。
- 首屏就给“推荐第一条 prompt”。
- 不强迫用户读长文档。

### 19.5 风险：输出太复杂

问题：为了严谨，生成过长内容，反而增加新手负担。

应对：

- 默认输出短版。
- 需要时展开详细版。
- 用固定结构降低阅读成本。

### 19.6 风险：无法证明省 token

问题：token 节省受工具、模型、项目复杂度影响。

应对：

- 不承诺固定百分比。
- 统计任务轮数、读文件数量、修改文件数量、返工次数。
- 用“减少 token 风险”替代“保证省 X%”。

## 20. 阶段路线图

### 第 0 阶段：项目定义

时间：1-3 天

目标：

- 确定项目名称
- 确定一句话定位
- 确定 5 个 MVP 场景
- 建立坏 prompt 案例库
- 写出第一版 Skill 说明

交付物：

- `PROJECT_ROADMAP.md`
- 项目名称候选
- MVP 场景清单
- 10 条坏 prompt 案例

### 第 1 阶段：Skill MVP

时间：3-7 天

目标：

- 创建第一个 Codex Skill
- 支持创意转路线
- 支持 prompt 体检
- 支持安全任务生成
- 支持发布检查

交付物：

- `skills/layman-project-navigator/SKILL.md`
- `references/prompt-scorecard.md`
- `references/task-patterns.md`
- `examples/bad-to-good-prompts.md`

成功标准：

- 能稳定把 10 条坏 prompt 改写成可执行任务。
- 输出不直接诱导 agent 做大范围修改。
- 新手能看懂下一步该做什么。

### 第 2 阶段：案例验证

时间：1-2 周

目标：

- 找 5-10 个真实小项目测试
- 比较使用前后的任务质量
- 收集用户反馈
- 优化模板和评分体系

测试项目类型：

- Todo App
- 背单词工具
- 个人博客
- 数据看板
- 小型自动化脚本
- 微信/网页小工具原型

指标：

- 是否减少模糊任务
- 是否更容易开始
- 是否减少大范围 diff
- 是否更容易验收
- 用户是否愿意继续使用

### 第 3 阶段：开源发布

时间：1 周

目标：

- 整理 README
- 提供安装说明
- 提供示例输入输出
- 发布到 GitHub
- 写一篇介绍文章或视频脚本

传播主题：

```text
别再让 AI “优化整个项目”。
把一句模糊创意，变成可执行的 Codex 任务。
```

### 第 4 阶段：CLI 原型

时间：2-4 周

目标：

- 增加本地项目扫描能力
- 自动识别技术栈和命令
- 生成项目感知 prompt

核心命令：

```text
layman init
layman analyze
layman plan
layman prompt
layman release-check
```

### 第 5 阶段：插件 / Web 形态

时间：1-3 个月

目标：

- 提供更低门槛的交互
- 提供 prompt 风险拦截
- 提供项目路线 UI
- 提供任务队列和历史记录

## 21. 第一版不做什么

为了避免失控，第一版明确不做：

- 不做一键生成完整项目
- 不做复杂 Web 平台
- 不做账号系统
- 不做支付
- 不做多用户协作
- 不做自动部署
- 不做强依赖某一个 AI coding 工具
- 不承诺固定 token 节省比例
- 不替代开发者 review

## 22. 第一版必须做什么

第一版必须做到：

- 能识别高风险 prompt
- 能把模糊创意拆成 MVP
- 能生成安全的第一步 prompt
- 能给出验收标准
- 能告诉用户不要现在做什么
- 能让小白知道下一步

## 24. 最小验证问题

在投入更多开发前，需要验证以下问题：

1. 小白是否能理解生成的路线图？
2. 小白是否愿意先规划再让 AI 写代码？
3. 生成的第一条 prompt 是否真的更容易执行？
4. 是否能减少 agent 乱读文件和乱改代码？
5. 是否能帮助用户从 demo 走到可发布？
6. 用户最愿意为哪个阶段付费：创意规划、项目扫描、发布检查还是维护？

## 25. 建议的下一步行动

建议按以下顺序推进：

1. 确认项目名称和定位。
2. 写 10 条真实坏 prompt。
3. 为每条坏 prompt 写目标改写结果。
4. 创建第一个 Skill 目录。
5. 编写 `SKILL.md`。
6. 编写 `prompt-scorecard.md`。
7. 用 3 个真实项目想法测试。
8. 根据测试结果调整输出格式。
9. 开源发布第一版。
10. 收集用户案例，再决定是否做 CLI 或插件。

## 26. 总结

本项目有明确现实需求：AI coding 工具降低了写代码门槛，但没有自动降低项目规划、任务拆解、验收和维护门槛。

项目小白真正需要的不是更华丽的 prompt，而是：

- 如何把想法变成 MVP
- 如何让 AI 一步一步做
- 如何防止 AI 乱改
- 如何判断 AI 是否做完
- 如何把 demo 变成可发布项目
- 如何长期维护项目

因此，最稳妥的产品路线是：

```text
Skill MVP
-> 案例验证
-> 开源传播
-> CLI / 插件
-> Web 项目导航器
-> 团队版和教育版
```

最终目标不是“省几句话的 token”，而是：

> 让普通人能更安全、更低成本、更可控地使用 AI coding agent，把创意真正落地成可维护、可发布的软件项目。
